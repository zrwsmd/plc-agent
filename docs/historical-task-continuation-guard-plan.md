# 历史任务承接守卫重构方案

## 状态

已按本文完成第一阶段实现与回归验证。生产守卫已改为按轮次判断任务关系；新任务只拦副作用工具复用历史资源，只读核验继续放行。后续如需调整任务归属启发式，应先补充对应任务级测试。

## 问题

当前历史参数守卫从历史对话和工具调用中提取资源，再在每一次工具调用前通过当前用户文本、工具风险、目标新旧、候选数量和成功回执判断是否拦截。该判断把“本轮任务是否延续”与“某个工具参数是否可用”混在一起，造成规则随场景增长，并误拦自然追问、只读核验和多步骤操作。

守卫的运行时接入点已经存在于 `runAgent()` 的工具调用检查中。守卫创建时也已拿到本轮原话和 session 历史。因此这次按边界收敛：重写 `agentHistory.ts` 中的判定逻辑，保留 `agent.ts` 的现有接线，不增加工具 schema、调用参数或澄清协议。

## 决策

### 按轮次判断任务归属

每轮创建守卫时，只做一次任务归属判断：本轮是否在延续最近的活动任务，还是开始了新任务。判断输入限于本轮用户原话和当前可读的 session 历史，不调用模型或外部服务。

延续轮次不再因工具参数曾出现在历史中而拦截。该轮的工具选择与具体目标由模型按本轮任务决定；工作区范围、权限审批、工具自身校验、重复调用收敛和 workflow 阶段约束仍照常执行。

新任务轮次只在副作用工具的参数复用了历史资源时拦截。历史参数检查不依赖工具名或目标字段白名单；只读工具不受这条历史复用守卫阻挡，以便模型读取、搜索和列举资源来核实目标。

### 保留新目标例外

新建/创建一个历史中不存在的新目标，应判为新任务，不能因上下文里有旧资源而把旧资源带入新目标操作。

不能只要出现“创建”就判成新任务。例如“基于刚才的记录创建报告”仍延续原任务，报告是任务的新产物。实现必须结合句子中的任务承接关系和新目标名称判断；若关系不确定，采用新任务分支的副作用参数拦截，并允许只读核验。

### 任务连续性不等于权限

“延续同一任务”只决定历史资源复用守卫是否介入，不授予工作区访问权、不批准高风险操作、不绕过工具或 workflow 的运行约束。原有授权边界、beforeEffect、审批、ToolCallDeduper 和 PipelineStageRuntime 不属于本次替换范围。

## 关键取舍

- 不新增持久化任务状态。普通新轮次按创建守卫时可见的 session 历史重新判定；同一 run 的 SDK 状态恢复和保留历史重试本来就跳过历史守卫。
- 不把恢复执行接入本方案。`agent.ts` 仅在 `initialState` 和 `preserveToolHistory` 都未设置时加载历史守卫。
- 上下文压缩不增加新的生产接口，但不能假设它与守卫无关。Coordinator 在执行 Agent 前会压缩 session，守卫随后从该 session 读取历史；压缩后的历史可能已不含原始工具条目。需用测试确认压缩后仍能正确区分延续与新任务；若不能，先调整摘要保留的历史事实，不引入新的跨轮持久化机制。
- 不增加工具 schema 目标字段声明。新任务分支的历史资源匹配使用通用参数值处理，不维护每个工具的字段名白名单。实现时需防止文件正文、搜索内容等普通参数文本因偶然提到历史路径而产生误报。
- 澄清链路本次不改。已有宿主选项值绑定继续保留；本方案只确保澄清后的用户选择不会因“必须有成功工具回执”或全局候选唯一性而再次被历史守卫否定。
- read-only、重复调用和 workflow 阶段策略是不同约束。开放只读核验不取消这些既有机制。

## 实施步骤

### 1. 固定新旧语义基线

先整理 `scripts/agent_kernel_test.mjs` 中直接构造守卫的用例，把每个用例标成继续任务、新任务、只读核验、权限/其他守卫。将继续任务里依赖成功回执、固定续接词、唯一历史目标的旧断言改写为新预期；保留真正的新任务旧参数拦截断言。

### 2. 替换守卫判定

在 `src/runtime/agentHistory.ts` 重写历史参数守卫：

1. 创建时计算一次本轮任务归属。
2. 延续任务不因历史参数匹配而拒绝工具调用。
3. 新任务仅拦截副作用工具的历史资源复用；只读工具通过该守卫。
4. 删除仅为旧判定服务的候选分组、成功回执分档、字段白名单和逐工具续接分支。
5. 保留清晰、单一的拦截提示，说明当前是新任务、参数疑似来自旧任务，并让模型按当前目标重新选择；不要同时要求澄清和禁止澄清。

不修改 `agent.ts` 的调用签名，不修改 `runCoordinator.ts` 或澄清协议，除非实施时发现当前接线无法表达上述行为；若发现必须扩展边界，先更新本文再动相邻模块。

### 3. 清理旧测试并补齐任务级回归

测试按一轮任务和完整工具序列组织，不再只断言单个参数字符串。必须覆盖：

- “继续修改刚才的文件”不重念路径，写入可以承接；无需成功工具回执。
- 多个历史文件存在时，延续轮次不会因全局资源不唯一而统一拦截。
- 新任务携带旧路径调用写入、删除或执行时会被拦截。
- 新任务的 read/list/search 可以核验旧路径，不触发历史守卫；后续副作用仍按当前目标和独立权限规则处理。
- 明确创建历史中不存在的新目标时，不继承旧目标。
- 基于历史对象生成新产物仍视为任务延续。
- 改名等写新/删旧多步操作，在用户明确要求延续任务时不会只完成一半。
- 澄清选项仍绑定宿主规范值；澄清不会授予额外工作区权限。
- 新任务的匹配不因正文或搜索词偶然出现历史资源而误拦。
- 历史被上下文压缩后，归属判断不因原始工具条目消失而改变为危险的错误放行。
- ToolCallDeduper、beforeEffect、权限审批和 PipelineStageRuntime 的现有测试继续通过。

当前 `scripts/agent_kernel_test.mjs` 中守卫构造调用有 30 处；需要按语义审查，而不是机械改写断言。

### 4. 验证和删除旧逻辑

运行 `npm run test:agent`、`npm run test:batch`、`npm run compile` 和 `git diff --check`。检查 `agentHistory.ts` 中旧规则专用常量、辅助函数和提示文案是否均已删除；确认其它权限、授权和 workflow 测试未改变语义。

## 风险与处理

主要风险是任务归属误判：把新任务判成延续可能让副作用参数继承旧资源；把延续任务判成新任务则会重复出现用户必须重说路径的问题。新目标例外降低前者，明确的自然续接和多资源用例降低后者。匹配规则不得退化为只看一个动作词；对“从旧对象派生新产物”和“开始一个无关的新对象”必须有成对测试。

第二个风险是通用参数扫描误报。测试需要包含正文/查询参数中提到历史名字的情况；若仅凭字符串比较仍误报，应在任务级资源集合的提取上收窄，而不是重新引入逐工具字段白名单。

第三个风险是压缩后的 session 不保留足够资源事实。若测试证实影响本轮任务归属，应让现有压缩摘要保留活动任务和关键资源引用；不因此建立独立的跨轮任务数据库。

## 本次不做

- 不新增任务数据库、跨会话任务 ID 或恢复状态字段。
- 不修改工具权限模型、工作区授权和 beforeEffect。
- 不扩大澄清答案协议或修改 Webview 行为。
- 不改模型提示来替代运行时守卫。
- 不提交代码或打包 VSIX。

## 完成标准

- 任务归属在每轮计算一次；逐工具检查只保留新任务的副作用历史参数阻断。
- 延续任务中的自然追问、多资源和多步骤操作不因旧历史匹配而误拦。
- 新任务复用旧副作用参数仍能在工具实现执行前被阻止。
- 只读核验可运行，独立权限和工作区边界仍有效。
- 旧规则的专用分支与对应断言已删除，必要的非相关安全守卫保持原样。
- 相关测试、批量测试和编译通过。
